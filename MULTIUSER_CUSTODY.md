# Общий кошелёк, отдельные пользовательские деньги — beta

`main.py` теперь маршрутизирует финансовые API в `CustodyRuntime`, а не в
однопользовательский `WalletRuntime`. Последний оставлен только как библиотека
проверенных RPC/SPL-примитивов; его owner-only обработчики не зарегистрированы.
Это реализация для проверки перед публичным запуском, не гарантия прибыли,
безопасности кастодиального бизнеса или пригодности к работе под большой нагрузкой.

## Что изменилось

- Telegram Init Data проверяется сервером. ID из query/body не выбирает владельца.
- Любой подтверждённый Telegram-пользователь получает отдельный счёт.
- Все пользователи пополняют один `DEPOSIT_WALLET`. Каждый платёжный запрос имеет
  случайный Memo `ZL1:<32-char-id>`, конкретный актив, точную сумму и срок 1 час.
- Страница `/deposit/<invoice>` готовит unsigned SOL или USDC TransferChecked.
  Кошелёк пользователя подписывает и отправляет перевод, сайт не принимает seed/key.
  В Telegram на iPhone есть переход в браузер Phantom через документированный browse
  deeplink. Ввод подписи вручную — резервный вариант, но **Memo обязателен**.
- Входящий перевод принимается только из Solana mainnet с `finalized`, без ошибки,
  с правильным Memo/суммой/активом. Зачисляется владелец сохранённого запроса, а не
  тот, кто первым прислал подпись. Повторная подпись не даёт второго зачисления.
- Сканируются общий адрес и USDC ATA; закрытие браузера не отменяет распознавание
  депозита. Подпись можно проверить в приложении вручную при задержке/сбое RPC.
- Доступные средства, инвестиции, резерв перевода и результат каждой подтверждённой
  сделки принадлежат одному пользователю. Покупка не клонируется другим пользователям.
- Деньги учитываются в целых микродолларах/лампортах/raw tokens, не float.
  Журнал двойной записи неизменяем; кэш остатков сверяется с журналом.
- Перед отправкой атомарно резервируются собственный актив пользователя и отдельный
  SOL-бюджет оператора на комиссию/ATA rent. Ни пользовательские SOL, ни чужие USDC
  не используются как операторский бюджет. Отрицательные пользовательские остатки
  запрещены, транзакция БД откатывается целиком.
- Сначала на persistent disk сохраняются подписанная транзакция и её подпись, затем
  идёт sendTransaction. RPC acceptance не считается завершением.
- UNKNOWN/PREPARED/SUBMITTED не освобождают резерв и не вызывают новый перевод.
  Повторный клиентский request_id возвращает ту же операцию. После подтверждённого
  неуспеха возвращается только собственный резерв, сетевая комиссия оплачивается
  оператором атомарно. После finalized success фиксируются фактические дельты.
- Полная симуляция защищает суммы остальных SPL-счетов, владельца системного кошелька,
  mint/authority/delegate и лимит расходов SOL. Для v0 getFeeForMessage получает
  правильную сериализацию versioned message.
- SOL и wrapped SOL при swap считаются вместе. Возвращённый ATA rent не становится
  пользовательской «прибылью»; преобразование чужого WSOL в native SOL не создаёт
  новые операторские деньги.
- Автоторговля, её размер и «закрыть все» относятся только к текущему аккаунту.
  Используется прежняя простая dip/TP/SL-стратегия; это **не доказанная прибыльная
  стратегия и не AI-гарантия лучших сделок**. При перезапуске торговля приостанавливается.
- Из обычных stats/logs убраны общие остатки, позиции и история других клиентов.
  Администраторские настройки дополнительно защищены серверным ID.
- Установленный PIN нельзя заменить без текущего PIN; смена не обходит блокировку
  после неправильных попыток.
- Чужой /webhook без Telegram secret header отклоняется; secret выводится из уже
  установленного bot token, дополнительный секрет вводить не требуется.
- В поле вывода нет предустановленного личного адреса разработчика.

## Миграция и первичная настройка

1. До первого создания custody-таблиц автоматически делается SQLite backup:
   `<DB_FILE>.pre-custody.bak`, права `0600`. Бэкап не публикуется, не заменяется.
   Проверьте отдельно внешнее резервное копирование persistent disk.
2. Старые `users.balance_usdc`, виртуальные сделки и owner-wallet позиции сохраняются,
   но **не становятся подтверждёнными деньгами нового реестра**. Старый pending платёж
   блокирует новые отправки до выяснения его исхода. Не удалять такие записи для
   «разблокировки».
3. `PUBLIC_CUSTODY_ENABLED` по умолчанию false. Все счета изолированы, но обычным
   пользователям запрещены пополнение/вывод/торговля до публичного открытия.
   Владелец может проверить **обычные** финансовые маршруты beta, не отдельный test endpoint.
   Для проверки второго аккаунта до открытия всему миру можно явно добавить его
   Telegram ID в `CUSTODY_BETA_USERS` (через запятую). Это не делает его администратором.
4. В интерфейсе владельца есть «Выделить собственные SOL на комиссии»: например 0.01 SOL.
   Перед действием он явно подтверждает, что переносимые нераспределённые монеты
   принадлежат ему, не клиентам. На одну операцию резервируется максимум 0.005 SOL;
   списывается только фактическая комиссия/создание ATA, остаток возвращается оператору.
   Нельзя создать этот резерв из уже учтённых клиентских требований.
   Если у владельца есть SOL на собственном счёте, сначала используется именно его
   доступный остаток. Так резерв можно пополнять обычным собственным депозитом SOL,
   не затрагивая чужие счета; только недостающая часть берётся из подтверждённых им
   нераспределённых собственных монет. При пустом резерве новые клиентские платёжные
   запросы приостанавливаются.
5. До публичного открытия старые **фактически имеющиеся собственные** USDC/SOL можно
   один раз по активу перенести в личный счёт через админ-кнопку. Ввести точную
   проверенную сумму и подтвердить отсутствие чужих денег. Это не автоматический
   импорт старого виртуального баланса. Пользовательские депозиты после открытия
   принимаются только через свои Memo-запросы.
6. Проверить обычные депозит/вывод SOL и USDC на mainnet, включая мобильную подпись;
   затем изоляцию двух реальных Telegram-аккаунтов и их истории/позиций. Здесь
   автоматические тесты использовали локальную БД/моки, **реальные монеты не отправлялись**.
7. Открытие публике — отдельное решение оператора: установить
   `PUBLIC_CUSTODY_ENABLED=true` в Render и применить deployment только после проверки.
   Также нужны эксплуатационное резервное копирование/мониторинг, независимая оценка
   защиты server key и юридических обязанностей публичного хранения/торговли.
   Нельзя обещать пользователям заработок.

Существующие TELEGRAM_TOKEN, SOLANA_PRIVATE_KEY, DEPOSIT_WALLET,
SOLANA_RPC_URL, persistent `/var/data` остаются. Какие именно имена ключа читает
`get_signer_keypair`, определяется существующим main.py; новые ключи/seed не нужны.
Jupiter API Key по-прежнему опционален и настраивается секретом, не в коде/чате.

## Важные ограничения beta

В Wallet владельца есть «Проверить старые операции»: повторная read-only сверка
показывает сохранённые подписи/статусы и ошибки RPC даже при невозможности прочитать
остаток. Подписи доступны только администратору. Финансовый запрос сначала сверяет
старую операцию, затем проверяет блокировку. Отсутствие результата в RPC никогда
не превращается автоматически в FAILED и не разрешает повторную отправку.
Задержка Telegram setWebhook больше не откладывает запуск сверки операций.

- Одна незавершённая исходящая операция на общий кошелёк. Это защищает реестр от
  конкурирующих отправок, но ограничивает пропускную способность.
- UNKNOWN с отсутствующей/истёкшей подписью требует оператора и достоверной проверки
  истории сети. Код намеренно не создаёт новый перевод и не возвращает резерв
  только из-за таймаута или отсутствия статуса. **Не удалять pending вручную.**
- Если wallet key используется вне приложения, внешний перевод может нарушить
  покрытие требований. Проверка покрытия останавливает следующие финансовые операции.
  Изолированный ledger не заменяет защиту общего серверного ключа.
- Максимум 100 адресов в полной симуляции; неподдерживаемые Token-2022/расширения,
  изменённые права SPL или неполные ответы RPC блокируют отправку.
- Один Memo-запрос — один перевод с точной суммой. Переводы без Memo, второй платёж
  по оплаченному Memo, неверная сумма/актив/срок не зачисляются автоматически.
  Не объявлять их средствами оператора: нужна ручная проверка и решение о возврате.
- Нельзя просто откатить на прежнюю owner-wallet версию после приёма публичных средств:
  она показывает всю кассу как личный баланс владельца. Сначала остановить операции,
  сохранить БД и проверить все обязательства.

## Проверки

Из корня репозитория:

```sh
python3 -m unittest discover -s tests -v
python3 -m py_compile main.py wallet_runtime.py custody_ledger.py custody_runtime.py
```

Новые тесты покрывают два аккаунта, Memo attribution/replay, приватность API,
HMAC/подмену ID, целочисленную бухгалтерию, конкурирующие резервирования,
повторные request_id, неизвестный/неуспешный/успешный исход вывода,
реальные дельты swap, отдельные комиссии, WSOL/rent, backup/migration и ограничения
симуляции. Сохранены regression-тесты SPL-примитивов прежнего runtime.
Inline JS основного интерфейса и страницы оплаты проверяется через node --check.
Прохождение этих проверок не устанавливает работоспособность мобильного кошелька
или исход mainnet-транзакции.
